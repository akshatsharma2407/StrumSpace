# ADR-001: StrumSpace Architecture & API Standards

**Status:** Accepted  
**Date:** 23 November 2026  
**Project:** StrumSpace – Guitar Academy Management System

---

## 1. Context

StrumSpace is a backend-focused management system for an offline guitar academy. The goal is to replace fragmented operational processes involving spreadsheets, notebooks, WhatsApp, and manual record keeping with a centralized, reliable system.

The project is also intended to serve as an industry-oriented backend portfolio project, demonstrating practical engineering skills, including:

- Python and asynchronous programming
- REST API development
- Database design and relational modeling
- Transaction management and data integrity
- Testing
- Docker and containerization
- Maintainable architecture and software engineering practices

The architecture should be realistic and production-oriented without introducing unnecessary complexity, premature abstractions, or infrastructure that is not justified by the project's requirements.

This ADR documents the architectural and API standards agreed upon before implementation.

---

## 2. Architectural Decision

### 2.1 Architecture style — Modular Monolith

StrumSpace will follow a Modular Monolith architecture.

The application will be deployed as a single backend application, internally divided into well-defined modules with clear responsibilities.

Each module will encapsulate its own functionality while remaining part of the same application.

The initial application will not be divided into microservices.

### Rationale

- Simpler development and deployment.
- Easier debugging and testing.
- Less infrastructure and operational overhead.
- Clear separation of responsibilities without distributed-system complexity.
- Allows future extraction of services if a genuine need arises.

The architecture must avoid tightly coupled modules. Modules should interact through well-defined interfaces and avoid unnecessarily accessing another module's internal implementation.

## 4. Asynchronous Programming

### Decision

StrumSpace will use an async-first programming approach.

Asynchronous programming will be used for I/O-bound operations, including:

- Database interactions
- External API requests
- Network operations
- Asynchronous file operations where appropriate

CPU-bound operations will not automatically be converted to asynchronous functions, as async does not inherently improve CPU-intensive processing.

### Implementation direction

- Use FastAPI async endpoints where appropriate.
- Use SQLAlchemy's asynchronous API.
- Use `AsyncSession` for database interactions.
- Use an asynchronous MySQL driver.
- Avoid blocking operations inside the event loop.

### Rationale

This project is intended to provide practical experience with asynchronous programming while supporting concurrent requests and I/O-heavy workflows.

Async will be used where it provides a meaningful benefit, rather than being applied blindly to every function.

---

## 5. Database

### Decision

MySQL will be used as the primary relational database.

SQLAlchemy 2.x will be used for ORM and database interaction, with Alembic managing schema migrations.

### Database access

- SQLAlchemy Async API.
- `AsyncSession` for session management.
- A managed connection pool.
- Session lifecycle scoped to individual requests.
- Repository layer responsible for database operations.
- Explicit transaction boundaries for operations that require atomicity.

### Data integrity

Data integrity will be enforced at multiple levels where appropriate:

- Database constraints
- Foreign keys
- Unique constraints
- Appropriate indexes
- Transactions
- Application-level validation

Critical business operations must not rely solely on application-level checks when database-level protection is possible and necessary.

### Transaction strategy

Operations involving multiple database changes that must succeed or fail together will be handled transactionally.

Examples include:

- Trial booking and slot capacity updates.
- Student enrollment and related records.
- Payment record creation and associated updates.

Concurrency-sensitive operations will be designed to prevent race conditions and inconsistent data.

## 6. Timezone Standard

### Decision

StrumSpace will use Indian Standard Time (IST), represented by the IANA timezone `Asia/Kolkata`, as its project-wide timezone.

The system is intended for an academy operating in India, and all scheduling and operational timestamps will follow IST.

### Standards

- API datetime values will use ISO 8601 format with the `+05:30` offset.
- Scheduling and booking operations will be interpreted in IST.
- Class schedules, trial bookings, attendance, and reminders will follow IST.
- The application and database will use a consistent IST interpretation.
- MySQL `DATETIME` values will be interpreted as IST by application convention, since the column itself does not store timezone metadata.

UTC conversion will not be part of our application workflow.

Timezone handling must be implemented consistently to prevent ambiguous datetime values.

## 7. API Standards

### 7.1 Versioning

APIs will be versioned from the beginning.

Initial API prefix:

`/api/v1`

Example:

- `/api/v1/enquiries`
- `/api/v1/students`
- `/api/v1/batches`
- `/api/v1/trial-bookings`

Versioning allows future changes to API contracts without unnecessarily breaking existing clients.

### 7.2 Resource naming

- Use plural resource names.
- Use lowercase URL paths.
- Use kebab-case for multi-word resource names.
- URLs should represent resources rather than actions.

Examples:

Preferred:
- `POST /api/v1/students`
- `GET /api/v1/students`
- `GET /api/v1/students/12`

Avoid:
- `/createStudent`
- `/getStudents`
- `/deleteStudent/12`

### 7.3 HTTP methods

| Method | Purpose |
|---|---|
| GET | Retrieve resources |
| POST | Create resources or initiate operations |
| PATCH | Partially update resources |
| PUT | Replace a resource when full replacement is required |
| DELETE | Delete resources |

PATCH will be preferred for routine partial updates.

### 7.4 Request and response format

JSON will be the standard format for API requests and responses, except where a different format is necessary, such as file uploads.

JSON keys will use snake_case.

Example:

{
  "student_id": 12,
  "batch_id": 4,
  "start_time": "2026-11-23T16:30:00+05:30"
}

Responses will use straightforward JSON structures. Unnecessary response wrappers will be avoided unless a specific requirement justifies them.

### 7.5 Success responses

Successful resource retrieval or creation will return the relevant resource representation.

Successful deletion, when no response body is needed, will return:

`204 No Content`

HTTP status codes will reflect the result of the operation appropriately.

### 7.6 Error handling

API errors will follow a consistent structure.

Example:

{
  "error": {
    "code": "ENQUIRY_NOT_FOUND",
    "message": "Enquiry not found.",
    "details": null
  }
}

Initial status code conventions:

| Status | Meaning |
|---|---|
| 400 | Bad request |
| 401 | Unauthenticated |
| 403 | Forbidden |
| 404 | Resource not found |
| 409 | Resource or business conflict |
| 422 | Request validation failure |
| 500 | Unexpected server error |

Errors should be meaningful to API consumers.

Internal implementation details, database errors, stack traces, and sensitive information must not be exposed in API responses.

## 8. Pagination, Filtering & Sorting

### Pagination

List endpoints will support pagination where appropriate.

Initial convention:

`GET /api/v1/students?limit=20&offset=0`

Paginated responses will use the following structure:

{
  "items": [],
  "total": 125,
  "limit": 20,
  "offset": 0
}

- `limit`: Maximum number of records returned.
- `offset`: Number of records skipped.
- A reasonable maximum limit will be enforced.

Pagination will be applied to suitable list endpoints rather than blindly to every endpoint.

### Filtering

Filtering will use query parameters.

Examples:

- `/api/v1/enquiries?status=new`
- `/api/v1/students?batch_id=4`

### Sorting

Sorting will use query parameters, with an initial convention of:

- `sort_by`
- `order`

Example:

`/api/v1/batches?sort_by=created_at&order=desc`

Only supported sort fields and directions will be allowed.

## 10. Authentication & Authorization

### Decision

OAuth2 bearer-token authentication is the intended authentication approach.

Authentication and authorization implementation will be deferred until the later stage of development, after the core business modules have been developed.

The system will eventually support appropriate access control for different types of users.

### Deferred considerations

The following will be designed when authentication implementation begins:

- Token issuance and validation.
- Token expiry.
- Password management, if applicable.
- Role-based or permission-based authorization.
- Access restrictions at endpoint and resource levels.
- Security-related error handling.
- Authentication-related testing.

Deferring implementation does not mean ignoring security during development. Endpoints and data access should be designed in a way that does not make future security integration unnecessarily difficult.

## 11. Project Structure

### Decision

The application will follow a feature-oriented modular structure with separation of responsibilities within each module.

Initial structural direction:

app/
    main.py
    core/
    modules/
        enquiries/
        bookings/
        students/
        batches/
        attendance/
        payments/

Each feature module may contain:

| Component | Responsibility |
|---|---|
| router.py | API routes and HTTP handling |
| schemas.py | Request and response validation |
| service.py | Business logic and workflows |
| repository.py | Database queries and persistence |
| models.py | SQLAlchemy database models |

The exact structure may evolve as the application develops.

Modules and files will be created when they are required rather than scaffolding the entire system upfront.

### Separation of responsibilities

- Routers should remain relatively thin.
- Services should handle business logic.
- Repositories should handle database operations.
- Schemas should define validation and API data contracts.
- Models should represent database structures.

Business logic should not be unnecessarily embedded in route handlers.

## 12. Database Modeling & ERD Strategy

### Decision

The complete ERD will not be designed upfront.

Database modeling will evolve alongside feature implementation.

Whenever a feature is introduced:

1. Identify the entities required.
2. Determine their attributes.
3. Define relationships.
4. Identify constraints and indexes.
5. Update the ERD.
6. Review the design before implementation.
7. Create the necessary migrations when implementation begins.

This approach allows the database design to remain grounded in actual requirements instead of speculative future features.

The ERD and database documentation must be updated as the schema evolves.

## 13. Testing Strategy

Testing will follow a layered approach.

### 13.1 Unit testing

Tests individual functions and business logic in isolation.

Examples:
- Business rule validation.
- Status transition validation.
- Calculation logic.
- Input-related business decisions.

### 13.2 Integration testing

Tests the interaction between components and the database.

Examples:
- Repository queries.
- Database persistence.
- Constraints and relationships.
- Transaction behavior.
- Rollbacks.

A real MySQL test database will be used for database integration tests where appropriate.

### 13.3 End-to-end testing

Tests complete workflows through the API.

Examples:
- Creating an enquiry.
- Booking a trial class.
- Enrolling a student.
- Recording attendance.

### Testing tools

- pytest
- pytest-asyncio
- HTTPX
- MySQL test database

### Testing principles

- Test meaningful behavior, not just code coverage.
- Include successful and failure scenarios.
- Include edge cases.
- Verify database constraints and transaction behavior.
- Test concurrency-sensitive workflows.
- Avoid blindly pursuing 100% test coverage.

---

## 14. Containerization

Docker will be used to containerize the application and its supporting infrastructure.

Docker Compose will be used for the local development environment, including the application and MySQL.

Container configuration should support a consistent, reproducible development environment.

Additional production-specific container configuration will be introduced when deployment requirements become clearer.

---

## 15. Background Processing

Background processing will not be unnecessarily introduced during initial development.

A separate worker process may be added when asynchronous jobs become necessary, especially for:

- Email notifications.
- Trial booking reminders.
- Payment notifications.
- Scheduled tasks.
- Retryable jobs.

The worker will remain part of the overall modular system rather than forcing a microservices architecture.

The job processing technology will be selected when the requirements justify it.

---

## 16. Development & Implementation Philosophy

The project will be developed incrementally.

- Implement one feature or meaningful slice at a time.
- Understand the requirements before writing code.
- Avoid premature abstractions.
- Avoid unnecessary dependencies.
- Preserve modular boundaries.
- Maintain data integrity.
- Write relevant tests.
- Document important architectural decisions.
- Review changes before moving to the next task.

The project owner will remain involved in architectural and implementation decisions to ensure the system is understood rather than blindly generated.

---

## 17. Decisions Deliberately Deferred

The following decisions are not finalized in this ADR and will be made when the requirements become clearer:

- Detailed authentication and authorization implementation.
- Exact token strategy and lifecycle.
- Complete ERD and all database tables.
- Detailed API payloads for every feature.
- Background job technology.
- File storage implementation.
- Deployment infrastructure.
- CI/CD configuration.
- Production observability stack.
- Detailed security implementation.
- Frontend technology.

These decisions should not be made prematurely.

---

## 18. Consequences

### Positive consequences

- Simple deployment model.
- Clear modular boundaries.
- Practical backend engineering experience.
- Consistent API conventions.
- Better maintainability.
- Stronger data integrity.
- Ability to incrementally evolve the system.
- Avoidance of unnecessary microservice complexity.

### Trade-offs

- Modular boundaries require discipline.
- Async programming introduces additional complexity.
- MySQL-specific behavior must be considered in database design.
- Deferred decisions may require revisions as new requirements emerge.
- A modular monolith requires careful management of cross-module dependencies.

These trade-offs are acceptable for the current project scope.

---

## 19. Final Decision Summary

The StrumSpace backend will be built as an async-first, modular monolith using Python, FastAPI, MySQL, SQLAlchemy 2.x, and Alembic.

It will expose a versioned REST API using JSON, follow consistent naming and error-handling conventions, use IST as its timezone standard, and adopt a layered, feature-oriented internal structure.

Database design, detailed API contracts, authentication, and supporting infrastructure will evolve incrementally alongside implementation, guided by actual feature requirements.

The objective is to build a maintainable, realistic backend while avoiding premature complexity.
